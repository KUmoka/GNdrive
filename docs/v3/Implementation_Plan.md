### データ境界

- `DriveDefinition`: Unit有無、基準値、Variant上書き、世代、個体差。負値・非有限値・不正係数をロード時検証。
- `DriveState`: 安定ID、推進/AG/Hover/TA/生成要求、Group番号・参加、Repose、枯渇ラッチ、Gen1再充填ロック、内部循環値。
- `VesselState`: SafeGuard、Field要求/停止ラッチ、加速度・回転配分設定。保存先と分離結合時の解決規則は後述。
- `StepInput`: Δt、kg質量、重心重力、地表相対速度、操縦入力・軸、操作船/packed状態、各Partのタンク状態、近傍物理船。
- `EffectPlan`: 支持/ブレーキ/推進のベクトル、回転Nm、Field対象別反発、予約Power、粒子費用。各値に単位を明記。
- `ResourceReceipt`: EC/粒子の要求・実取得・実生成・実消費・返却受入・貯蔵受入・受入不能余剰。
- `StepResult`: 確定状態、支払済みN/Nm、Field保護有無、演出入力、制限理由。コア計算と外部決済を追跡できるtick IDを付ける。
- `IResourcePort`: 領域スナップショット、要求量に対する実取得量/実受入量を返す。KSPの負数による貯蔵規約は接続層内へ閉じ込める。

Unitは資源APIを直接呼ばない。VesselSimulationだけが決済の順番を管理し、計画の再評価は決済済み実績を使う。コアはポートのインターフェースにのみ依存し、試験では部分供給・受入拒否を再現する。

## 4. 一ステップの実装契約

1. 構成変更をまとめ、安定ID順のGN一覧・重複を除いたRigidbody一覧を再構築。
2. 同tick・同種・同対象の命令をまとめ、適用可否を全対象検査してから状態を変更。
3. 有限の正Δt等を検証し、入力・資源・ロック状態を読み取る。
4. 稼働条件と同調係数を確定。Hover優先でAGと排他。TAはPowerだけに倍率を適用。
5. 支持→ブレーキ→推進/回転同順位→Fieldの要求を計算。出力予約と粒子費用を分ける。
6. TD発電量と粒子生成能力を独立計算。効果需要＋貯蔵空きに応じた生成量を計画する。満杯でも同tick消費へ生成を回せる。
7. TD発電をEC需要へ直接充当し、EC不足差分を一度取得。実ECから生成を確定。余剰ECは受入実績と廃棄へ分離。
8. 実生成＋利用可能備蓄を予算とする。SafeGuardでは実生成のみ。必要な優先順位で効果を縮小。
9. `max(実消費候補−実生成,0)` を一度だけ粒子取得。実取得不足は効果適用前に再配分。
10. TAの制約内要求に対する資源不足を判定し強制解除。通常Powerで再計算するが追加取得しない。返却受入不能分も記録。
11. 粒子余剰の貯蔵・返却を実績化。枯渇とField停止を確定し、支払済み効果だけを物理適用。
12. 保存・UI・演出へ結果を公開。非操作船/packedでは通常物理を適用しない。

生成率とEC/粒子が異なる複数生成器の配分には、暫定として安定ID順を採用する案。効率最適化は別課題とし、順序独立試験では入力列の並べ替えで結果が変わらないことを確認する。能力上限やSafeGuardによる制限と、取得不足を別の理由コードにする。

### 予算上の必須不変条件

- 共通並進上限は `min(合計Power[kN], 質量[kg]×設定加速度/1000)`。TAで最大G寄与そのものを増やさない。
- 並進費用は合成力のノルム×Δt。予約Powerは各優先枠から差し引き、後段の相殺で取り戻さない。
- 支持に逆らう下向き推進を除去する。配分探索の内積非負条件を検証し、違反を黙って二分探索へ渡さない。
- 支持/ブレーキ後の回転予約は入力ゼロでも推進へ返さない。RCS OFF時は回転枠ゼロ。粒子不足なら推進と回転を同率縮小。
- Field維持費は直径二乗、反発は各対象ごとの `2|F|Δt`。維持・必要反発費が払えなければ当tickからField OFF・保護解除。
- Field枠は対応ドライブのPowerだけ。上位予約をField対応Powerから先に引く保守的帰属を守る。
- `期末 = 期首 + 実生成 − 実消費 − 受入不能余剰`。TA再計算を含め一tick内で二重取得しない。
- 要求がゼロというだけで枯渇停止しない。需要に対する実供給ゼロと、計画的制限によるゼロを区別する。
- 同一Rigidbodyへ並進加速度を一度だけ適用。N/NmからKSP実APIの単位へ変換する箇所を一箇所に固定し、実機で検証。

## 5. 保存・ライフサイクルの追加設計案

以下は仕様にない運用上の詳細を埋める提案であり、確定要求とは区別する。

- 保存にはschemaVersionを付け、新規初期化とロードを分離する。内部EC/循環粒子のcfg初期値は新規生成だけに使う。
- Vessel共通値の保存方式はVesselModule API検証後に確定。Partへのバックアップが必要なら同じrevisionのスナップショットを保持する。
- 分離時は直前の共通設定を両船へ継承。結合時は安定ID最小のGNModule側の設定を代表とする案。どちらも物理適用前に一覧を再構築。
- Group0は各Vessel内で再構成する。結合で異なる群状態が衝突した場合は同調命令と同じ全対象検査を行い、禁止状態を部分コピーしない。
- 構成変更、破壊、off-railsでキャッシュを無効化。購読解除とField保護解除は破棄・船切替・エラー経路も共通化。
- packedでの変換は接続側の固定更新が呼ばれる範囲に限定し、未ロード期間の補填を追加しない。
- 初期版は対応外流路を明示エラー。TD同Part判定とGN粒子の共有引落しを混同しない。

## 8. ローカルLLMを使う具体的な開発手順

接続確認済み: `http://127.0.0.1:1234/v1`、指定モデルID `qwen/qwen3.8-27b`。モデル一覧の一致を確認した。別モデルへ自動フォールバックしない。

1. 最初に全仕様を一度渡し、危険箇所のレビューを取得する。生の応答と採否を保存する。
2. その後は1依頼を「1つの振る舞い、関連する1〜3ファイル、対応テスト」へ限定。必要な仕様節と確定インターフェースだけを渡す。
3. 入力は目的、仕様節、既存型、変更可能ファイル、非対象、受入例、出力形式の順に固定する。全リポジトリを毎回投入しない。
4. 生成されたパッチをレビューし、単位・状態遷移・決済回数を確認してから適用。モデルにシェルやファイル変更を直接任せない。
5. ビルド・意味のあるテストを実行し、失敗した試験名と必要最小限の差分だけを返す。2回修正して解消しなければ、仕様/契約の切り分けを先に行う。
6. temperature 0.2を初期案とし、実測の応答時間・トークン数・採用差分・手直し量を記録する。今回の設定を品質最適と断定しない。
7. 27Bモデルのメモリ使用や待ち時間を避けるため、最初は逐次依頼。コンテキスト上限・速度・量子化は未確認なので実測して調整。
